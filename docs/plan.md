## 1. 项目背景

### 1.1 为什么自建

日常需要远程操作公司电脑，但不放心向日葵这类第三方远控工具——桌面画面、键鼠操作全部经过厂商服务器，而本机上有敏感资料，风险不可接受。

解决思路：**流量只走自己可控的链路**（自己的 VPS 中继 + 端到端加密），不经过任何第三方。

### 1.2 目标（唯一目标）

> **在家里那台 Windows 上，能看到并操作这台公司电脑。**

只要这一件事跑通即算达成。Phase 2 结束时这个目标就实现了。

### 1.3 明确不做（避免范围蔓延）

- ❌ 文件传输（后续可加）
- ❌ 多设备管理、设备 ID 分配、设备发现
- ❌ 多用户、权限分级、审计日志系统
- ❌ 手机端、浏览器端（后续可加）
- ❌ 追求“看视频级”的流畅度

## 2. 角色与部署拓扑

| | 机器 | 角色 | 交付形态 |
|---|---|---|---|
| 被控端 | **本机（公司电脑）** | Agent | 开发期跑源码 → 稳定后打包 exe + 开机自启 |
| 控制端 | 家里 Windows（Windows） | Viewer | **exe**，双击 → 输密码 → 看到并操作画面 |
| 中转 | 野草云 Debian VPS（境外节点） | Relay | systemd 常驻，443，**只转发密文** |

### 关键环境事实

| 项 | 情况 | 影响 |
|---|---|---|
| VPS 地区 | **境外（香港 / 美国）** | 无 ICP 备案问题，80/443 可正常使用 |
| VPS 带宽 | **3~5 Mbps** | 压缩策略必须按低带宽设计；目标场景锁定「办公/运维」 |
| 域名 | **无，只有 IP** | TLS 走自签 + 钉扎；可选升级 Let's Encrypt IP 证书 |
| 被控机权限 | **有管理员权限，但按“无权限”设计** | 少一个失败面，兼容性最好 |
| 开发位置 | **在被控机（公司电脑）上开发并运行 Agent** | 便利，但带来键鼠被夺走的风险，见第 10 节 |

## 3. 技术决策（全部锁定）

| 项目 | 决定 | 理由 |
|---|---|---|
| 语言 | Python 3.11+（Agent / Viewer / Relay 同一语言） | 采集快、注入能力强、开发最快；一套语言维护三端 |
| 传输 | WebSocket over TLS（`wss`） | 外观即普通 HTTPS；后续浏览器端可复用 |
| 端口 | 主用 **443**，回退链 `443 → 8443 → 80 → 8080 → 22` | 443 最易穿防火墙且最不显眼；回退链解决可用性 |
| 加密 | **应用层端到端 AES-256-GCM**（主保障）+ TLS（传输伪装层） | 中继无密钥，看不到明文 |
| 密钥 | 共享密钥 → Scrypt 派生 PSK → HKDF(双方 nonce) 派生会话密钥 | 密码不当密钥直接用，防暴力破解 |
| 证书 | 自签 + 指纹钉扎起步；可选升级 Let's Encrypt IP 证书 | 无域名也能跑；钉扎不作为前置条件（见 8.2） |
| 采集 | **`dxcam`（DXGI 桌面复制）**，失败回落 `mss`（GDI） | 实测 dxcam 有新帧 4.65ms / 静止 0.11ms；mss 恒定 33ms。**差 7 倍** |
| 压缩 | 分块差分 → 只编码变化块 → **拼成 atlas 单次 JPEG** → 自适应质量/帧率 | 办公场景画面大部分时间静止，实测更新包中位仅 3.3KB |
| 降采样 | **只允许整数倍**（`reduce(k)`）。非整数倍 resize 会吃掉全部收益 | 🔴 实测陷阱：2560→1920 要 34.7ms，比不缩放还慢 |
| 注入 | `pywin32` `SendInput`，键用扫描码，鼠标坐标归一化 | 尊重目标键盘布局；归一化坐标不惧缩放 |
| 打包 | PyInstaller → 单文件 exe | 家里那台免装 Python |
| UI | Viewer 用 PySide6 / Tkinter 窗口 | 简单够用 |

## 4. 架构

```
 ┌──────────────────┐                                  ┌──────────────────┐
 │  家里 Windows     │                                  │  本机(公司电脑)    │
 │  Viewer.exe      │                                  │  Agent           │
 └────────┬─────────┘                                  └────────┬─────────┘
          │  wss://VPS:443 (主动外连)                             │  wss://VPS:443
          │                                                      │  开机自启 + 断线重连
          │                                                      │
          └──────────► ┌────────────────────┐ ◄────────────────┘
                       │  VPS Relay (Debian) │
                       │  · 同 room 两条连接即配对 │
                       │  · 全程只转发密文      │
                       └────────────────────┘
```

### 配对机制（极简）

两端配置同一个 `VPS 地址 + 房间号(room) + 共享密钥`。Relay 发现同一 room 内出现两条连接，直接对接转发。

**没有**设备 ID、没有发现机制、没有信令协商、没有多会话。

### 为什么 Agent 只往外连

公司网络无法被外部主动连入（NAT），因此 Agent 启动后**主动外连 VPS** 并保持长连接。好处：

- 本机**不开放任何入站端口**，无可被攻击的入口
- 不需要改防火墙规则
- 不需要管理员权限

## 5. 数据流

**画面方向（Agent → Viewer）**

```
mss 采集 → 缩放 → 与上一帧做 64×64 分块差分 → 只挑变化块
   → JPEG 编码 → AES-256-GCM 加密 → wss 上传
   → Relay 盲转（无密钥）→ Viewer 解密 → 拼图渲染到窗口
```

**控制方向（Viewer → Agent）**

```
Viewer 捕获本地键鼠 → 归一化坐标/扫描码 → AES-256-GCM 加密 → wss 上传
   → Relay 盲转 → Agent 解密 → SendInput 注入
```

## 6. 消息协议（草案 v0）

| 方向 | 类型 | 内容 |
|---|---|---|
| Agent → Viewer | `FRAME` | 变化块集合（每块的 x/y/宽高 + JPEG 数据）；或全量关键帧 |
| Agent → Viewer | `META` | 屏幕分辨率、缩放比、当前鼠标位置、编码参数 |
| Viewer → Agent | `MOUSE` | 归一化坐标 0~1、按键、滚轮 |
| Viewer → Agent | `KEY` | 扫描码、按下/抬起、修饰键 |
| Viewer → Agent | `CTRL` | 请求关键帧、调整画质/缩放、切换只读模式 |
| 双向 | `PING/PONG` | 保活 + **RTT 测量**（自适应码率的依据） |

后续细化后落到 `docs/protocol.md`。

## 7. 关键技术方案

### 7.1 屏幕采集
**首选 `dxcam`**（DXGI Desktop Duplication），失败自动回落 `mss`（GDI）。实测差距极大：

| 后端 | 有新帧时 | 画面静止时 |
|---|---|---|
| **dxcam (DXGI)** | **4.65 ms** | **0.11 ms** |
| mss (GDI) | 33 ms | 33 ms（无论是否变化都要付） |

dxcam 在画面无变化时 `grab()` 返回 `None` —— 静止时**几乎零开销**，这对办公场景（大部分时间静止）是决定性优势。

**必须保留 mss 回落**，因为 DXGI Desktop Duplication 有两个硬限制：
1. **每个显示器只允许一个复制器** —— 被 OBS / 录屏软件占用时会失败
2. **RDP 远程会话下不支持**

采集后立即缩放到目标分辨率（默认原生，见 7.2）。`dxcam` 用 `processor_backend="numpy"` 可绕开对 opencv 的依赖。

### 7.2 压缩（Phase 0b 实测后定稿）

- 画面切成 **64×64 tile**，用 numpy 与上一帧比较，只保留变化超过阈值的 tile
- **把变化块拼成一张 atlas，只做一次 JPEG 编码** —— 实测比逐块编码**省 44% 体积**，且只需一次编码调用
- **静止画面更新包几乎为 0** —— 实测办公场景（打字、看文档）更新包中位仅 **3.3 KB**
- 定期（约每 2 秒）或按请求发一次**全量关键帧**，修正累积误差
- **自适应**：依据 RTT 与发送队列长度，动态调整「JPEG 质量(40~80) / 帧率上限 / 缩放比例」

**差分算法性能关键**：把颜色通道并入 tile 归约（`max(axis=(1,3,4))`），
而不是常见的 `d.max(axis=2)` 后再归约。后者在 numpy 里对小尾轴归约开销极高：

| 算法 | 原生 2560×1408 耗时 |
|---|---|
| `np.abs(a.astype(int16) - b.astype(int16)).max(axis=2)` 再归约 | 118.2 ms |
| **`(maximum - minimum).max(axis=(1,3,4))`** ✅ | **15.4 ms** |

检出结果完全一致（都是 209 块），**快 7.7 倍**。

**编码方式取舍**（实测）：

| 方式 | 结果 |
|---|---|
| **JPEG q60** ✅ | 甜点。q45 体积只小一点但画质明显下降，q75/q80 体积涨得快 |
| WebP q75 | **179 ms** 编码，慢到不可用 ❌ |
| PNG | 535 KB / 26 ms，又大又慢 ❌ |

**降采样的硬性约束**（实测陷阱）：

| 目标 | 方式 | 预处理耗时 | 单帧合计 |
|---|---|---|---|
| 2560×1408 原生 | 不缩放 | 0.01 ms | **29.7 ms** |
| 1920×1056 | `resize BOX`（非整数倍） | **34.7 ms** ❌ | 50.3 ms |
| **1280×704** | **`reduce(2)`（整数倍）** ✅ | 13.3 ms | **23.6 ms** |

> **降采样必须走整数倍。** 2560→1920 不是整数倍，通用 resize 的代价高到
> 比不缩放还慢 —— 这是个容易踩的坑。

### 7.3 加密与密钥

1. 用户设一个共享密码
2. `PSK = Scrypt(密码, salt)` —— 密码不直接当密钥
3. 两端各自生成随机 nonce，经 Relay 明文交换（nonce 无需保密）
4. `会话密钥 = HKDF(PSK, nonce_agent || nonce_viewer)` —— **Relay 无 PSK，无法派生，因此看不到明文**
5. 每帧 AES-256-GCM 加密，带序列号 + GCM nonce 计数器（抗重放）

### 7.4 传输与端口

- WebSocket over TLS，默认 443
- 连接失败按回退链依次尝试 `8443 → 80 → 8080 → 22`
- 端口是**一行配置项**，Phase 0a 实测后确定

### 7.5 输入注入

- 鼠标：归一化坐标 0~1 → 按 Agent 端实际分辨率还原，不惧缩放
- 键盘：发送**扫描码**而非字符，尊重目标机器的键盘布局
- 用 `SendInput`（比 `keybd_event`/`mouse_event` 更底层可靠）

### 7.6 打包与自启

- PyInstaller 打包 Viewer 与 Agent 为单文件 exe
- 开机自启走**启动文件夹**或**用户级计划任务**，不依赖管理员权限
- Agent 提供托盘图标；断线按指数退避自动重连

## 8. 端口与安全性的关系（重要说明）

### 8.1 端口不影响安全强度

安全性来自**加密算法和密钥**，不来自端口号。443 换成 8080、换成任意端口，加密强度完全一致。

```
画面/键鼠 ──► AES-256-GCM 加密 ──► TLS ──► 走任意端口 ──► VPS 盲转 ──► 解密
              ↑ 真正的安全保障在这里        ↑ 端口在这，只是个门牌号
```

端口真正影响的只有两件事：**① 能不能穿公司防火墙 ② 会不会被注意到**。

| 端口 | ① 穿防火墙 | ② 隐蔽性 | ③ 安全性 |
|---|---|---|---|
| **443** | ★★★★★ 几乎必放行 | ★★★★★ 就是标准 HTTPS，最泯然众人 | **同样强** |
| 8443 | ★★★★ 多数放行 | ★★★★ HTTPS 备用端口，常见 | **同样强** |
| 80 | ★★★★★ 几乎必放行 | ★★★☆ 明文 HTTP 端口上跑 TLS，略怪 | **同样强** |
| **8080** | ★★★★ 多数放行 | ★★★★ HTTP 备用端口，非常常见 | **同样强** |
| 22 | ★★★ 看策略 | ★★★ SSH，可能被重点审计 | **同样强** |
| 随机高位端口 | ★☆ 常被直接拦 | ★☆ 容易被当成木马回连 | **同样强** |

第 ③ 列全部相同 —— 这就是结论。

### 8.2 反直觉点：443 比 8080 更“低调”

安全设备（NDR/EDR）有一条经典规则：**往非标准端口发持续加密流量 = 木马回连的典型特征**。所以用随机高位端口反而更容易被标记。

- **443 最优**：混在海量正常 HTTPS 流量里，最难分辨
- **8080 也没问题**：很多公司内部系统就用它，不算异常
- 端口回退链解决的是**可用性**（443 被堵时还能连上），不是安全性

### 8.3 为什么 TLS 不作为安全前置条件

因为已有应用层端到端加密，TLS 只是“穿墙的马甲”。这带来一个很好的性质：

- 公司**没做** TLS 中间人 → 正常加密，安全
- 公司**做了** TLS 中间人解密 → 连接照样能用（代理解出来的是 AES-GCM 密文），**依然安全**

反之若采用“自签 + 严格钉扎”，公司代理解密 TLS 时连接会直接失败，项目就死在公司网络上。因此钉扎只作为起步手段，不作为硬性前置条件。

### 8.4 公网 VPS 会被扫描

公网 IP 无论开什么端口都会被全网扫描器扫到，这是常态、无法避免。但 Relay：

- 只接受握手成功、验证过密钥的连接，握手超时即断开
- 即使被连上，也只是转发密文，拿不到任何内容

因此“被扫到”本身无危害。后续可选加固：fail2ban、握手超时、连接数限制。

## 9. 安全设计清单

1. **端到端 AES-256-GCM** ← 核心。Relay 无密钥，VPS 被入侵也读不到内容
2. **Scrypt 强密钥派生** —— 密码不当密钥直接用
3. **序列号 + GCM nonce 计数器** —— 抗重放
4. **Agent 零入站端口** —— 本机不监听，无可攻击入口
5. **Relay 只认认证连接** —— 握手超时踢掉，只转发密文
6. **TLS 仅作伪装层** —— 被中间人解开也只是密文
7. **免安装、不依赖管理员权限** —— 减少系统层面改动
8. **可选加固**：Relay 加 IP 白名单 / fail2ban / 连接限速

## 10. ⚠️ 保命措施（第一版就带，不可延后）

**背景风险**：开发在被控机上进行，而 Agent 的核心职能是「抓屏 + 夺取键鼠」。一旦代码有 bug，可能**夺走开发者自己的鼠标键盘**——远程注入的鼠标在本机乱点、键盘乱输入，而人却无法用键鼠去关掉它。这在本机调试时是真实会发生的。

| # | 措施 | 说明 |
|---|---|---|
| 1 | **本地急停热键** `Ctrl+Alt+Shift+Q` | 立即停止注入 + 断开远程会话。**必须实现** |
| 2 | **只读模式开关**（`allow_input=false`） | 首次测试与回归测试默认开启，只看不动 |
| 3 | **空闲自动断连** | 远程 60 秒无操作自动断开（可调） |
| 4 | **本地活动检测** | 检测到本机有人操作键鼠时，暂停远程注入（避免“抢方向盘”） |
| 5 | **注入目标限定** | 首次测注入只针对专门的白窗口，不全屏乱动 |

**实施纪律**：Phase 1 先做纯只读画面，确认采集/传输稳定后，Phase 2 才开输入注入。

### 两个必须如实说明的现象

**1. 链路有偶发丢包，会出现 0.5~2 秒的尖峰**

表现为 TCP 重传超时（实测到 1062ms、1109ms、2081ms 这类接近指数退避的数值）。
基础延迟很健康（50-130ms），但约一半的采样点会撞上尖峰。

> **注意上面那次测量放大了它**：因为 Agent 与 Viewer 都跑在同一台机器上，
> 视频路径是 `本机→VPS→本机`，**两次穿过同一条有丢包的链路**。
> 真实部署是 `公司→VPS` 与 `VPS→家里` 两条不同链路，视频只穿公司那条一次，
> 所以实际体验会好于表中数字。

**2. 周期性关键帧占了一半流量**

31 个关键帧 × ~137KB ≈ 4.25 MB，占总量 8.29 MB 的 **51%**。
办公场景画面大部分静止，但"每 2 秒补一个整屏关键帧"反而成了流量主体。

**但不建议改**：1.16 Mbps 对比 19 Mbps 可用上行远不是瓶颈，
而关键帧是丢包后的兜底，2 秒的恢复速度比省这点流量更值。

> 另外确认了一件好事：**整轮 0 丢帧**。因为帧很小（平均 7.5 KB），
> websockets 的写缓冲（默认 32KB）加我们自己的发送队列（8 帧）足以吸收尖峰，
> 网络恢复后自动追上，不会累积延迟。

### Phase 4 多显示器支持的设计要点

**问题**：键鼠注入需要知道「采集的是哪块屏、它在虚拟桌面上的位置」，但
dxcam **不暴露这个偏移**（它的 ``region`` 是输出本地坐标，恒从 0,0 开始）。
所以副屏上注入会错位 —— 本机正好是双屏（2560×1440 主屏 + 1920×1080 副屏），
所以这是个真实会遇到的问题。

**做法**：靠 mss 的显示器枚举（它给出 left/top）按尺寸还原位置。
策略从可靠到不可靠依次尝试：

1. **按分辨率唯一匹配** —— 最可靠，而且不依赖解析 dxcam 的调试字符串
2. 分辨率有重复时，用 dxcam 的 ``Primary`` 标志区分
3. **都不行就返回 None** —— 宁可不给，也不要给错。注入位置错了比不注入更糟

本机实测：``Output[1] (1920x1080) -> (2560, 566, 1920, 1080)``，
副屏那个之前"无法确定"的偏移量被正确还原（注意纵向也有 566 的偏移）。

**为什么必须写单元测试**：本机只有一种双屏布局，
**分辨率相同、旋转、无匹配**这些情况根本复现不了 —— 而它们恰恰最容易出错。
所以用合成数据把分支全覆盖，包括「不敢确定时必须拒绝」。

### 为什么必须做长期运行测试

这个工具的用法是**开机自启、常驻一整天**，而每次会话都会新建采集线程、
剪贴板监听线程、急停热键线程，以及一堆协程与 socket。只要有一处回收不干净，
跑几小时就会线程数持续上涨、句柄耗尽、内存被吃光 —— 而**这类问题在短测试里完全看不出来**。

测试做法：反复强制断开重连 5 轮，把「建 → 用 → 拆」这条路径跑很多遍，
并在**会话运行中**与**拆除之后**各采一次样对比。

实测结果（单位：线程 / 句柄 / 内存）：

| | 基线 | 运行中 | 结束后 |
|---|---|---|---|
| 第 1 轮 | 1 / 172 / 43.1MB | 4 / 189 / 53.3MB | 1 / 176 / 50.3MB |
| 第 5 轮 | — | 4 / 189 / 55.2MB | 1 / 176 / 50.6MB |

线程完全回收（4 → 1），句柄仅残留 4 个且不随轮次增长，内存持平。
**可以放心常驻。**

> 一个容易忽略的测试陷阱：只在拆除后采样的话，
> 结果永远是「1 个线程、没泄漏」—— 即使被测代码**根本没创建过线程**。
> 所以必须同时采样运行中的状态来证明测试有效。这个测试自己也被这个坑绊过一次。

### Phase 4 代理兜底的设计要点

**为什么必须做**：公司网络「要求经代理才能出网」非常常见。只做直连的话，
一旦直连被拦就会得出「这条路走不通」的错误结论 —— 而实际上经代理是通的。

**策略**：直连永远排第一（不经第三方、链路最短），全部端口都不通才落到代理。
``websockets`` 原生支持 HTTP CONNECT 与 SOCKS，但**只认环境变量**，
不读 Windows 的 IE 代理设置（注册表）和 WinHTTP —— 而公司电脑配的代理通常恰在那里。
所以 `src/common/proxy.py` 自己探测这三处。

**测试方式**：起两个假代理（HTTP CONNECT + SOCKS5）做**真实转发**，
并把目标设成「直连必然失败、只有经代理才能到达」的地址。
否则直连先成功，代理根本不会被尝试，测试就成了自我安慰。

### 两个真实踩到的坑

1. **代理健康检查不能只看状态行**。实测本机的 xray（v2rayN 混合入站）
   对**根本不可达的目标也先回 `200 Connection established`**，之后才失败。
   `probe_agent` 因此一度误报「代理可用」。现已改为**建立隧道后必须再做一次真实往返**
   才算通 —— 只看状态行的检查会给出假阳性，那比不检查更糟。
2. **`python-socks` 会在本地解析主机名**。走 SOCKS 时中继地址必须本机可解析
   （IP 或真实域名）。本项目默认用 IP，所以实践上不受影响，但已在文档里写明。

### Phase 4 剪贴板同步的设计要点

**回环（echo）是这里唯一真正的难点**：双向同步时，
A 写入剪贴板 → 监听到变化 → 同步给 B → B 写入 → B 又监听到变化 → 同步回 A → 无限互相覆盖。

防护办法：**写入剪贴板的同时把内容记为「已见」**，
且这个「写 + 记」必须与「读 + 比对」互斥（同一把锁）。
否则会出现「读到旧值 → 认为变了 → 把旧内容发回去」的竞态。

测试里专门用假剪贴板后端覆盖了这一点，包括**高频并发写入**的场景（1.2 秒内不间断写入，
监听线程一次都没有误报）。

**另一个被测试抓到的健壮性问题**：读写函数一旦抛异常（Windows 上剪贴板被别的程序
占用时很常见），监听线程会**静默死掉** —— 同步从此失效且毫无提示。
现已用 `_safe_read()` 兜住所有异常并计数，线程永不因异常退出。

> 剪贴板同步**不依赖 `--enable-input`**：它只是双向搬运文本，不属于「操作目标机」。
> 想让对端完全看不到你的剪贴板，就关掉 `clipboard_sync`（或 Viewer 加 `--no-clipboard`）。

### Phase 3 打包踩到的坑（值得记下）

**dxcam 的编译扩展没被打进 exe，导致打包后采集彻底失效。**

现象：Agent exe 启动后报 `ModuleNotFoundError: No module named 'cv2'`，
而源码运行时完全正常。

根因：dxcam 的 numpy 后端是一个**动态加载**的编译扩展
（`dxcam/processor/_numpy_kernels.cp313-win_amd64.pyd`），
PyInstaller 的静态分析发现不了它。运行时找不到该扩展，dxcam 就**静默回落**到
需要 opencv 的 cv2 后端 —— 于是采集全废。

对策：`--collect-all dxcam`（同时 `--collect-all comtypes`，它也会动态生成模块）。

> 这个坑是靠给打包产物加的 `--selftest` 抓出来的。如果没有自检，
> 它会一路带到公司电脑上才发现，而且报错信息（"没有 cv2"）完全指不到真正原因。

### Windows 上的两个环境坑

1. **`.ps1` 必须带 UTF-8 BOM**：Windows PowerShell 5.1 按 ANSI（中文系统 GBK）
   读取无 BOM 的脚本，中文乱码并直接把字符串引号吃掉 → 语法报错。
2. **原生命令写 stderr 会让 `$ErrorActionPreference='Stop'` 中断脚本**：
   PyInstaller 把 INFO 日志写到 stderr，导致"一切正常却中断"。

两者都已在 `scripts/build_exe.ps1` 与 `.editorconfig` 中处理。

### Phase 2 的保命措施实现要点

| # | 措施 | 实现方式 |
|---|---|---|
| 1 | 急停热键 | `RegisterHotKey`（**不装键盘钩子**，对系统影响最小、AV 不敏感）。触发后暂停注入 + 松开所有按键 + **彻底停止 Agent**（连重连也停掉，需手动重启） |
| 2 | 只读模式 | `allow_input=false` 时**根本不创建注入器**，键鼠事件明确记数并丢弃 |
| 3 | 空闲自动断连 | 心跳超时后断开并 `release_all()` |
| 4 | 本机活动检测 | 注入后记录光标应有位置，下次注入前比对实际位置；偏离超阈值即暂停。**不需要钩子就能区分「注入的移动」与「本机手动的移动」** |
| + | 断线释放 | 任何断线路径都调 `release_all()`，避免远端留下卡住的按键 |
| + | 演练模式 | `input_dry_run=true` 只记录不执行，安全验证整条注入链路 |

> **注入细节**：鼠标用**绝对坐标 + 虚拟桌面**（`MOUSEEVENTF_ABSOLUTE | VIRTUALDESK`），
> 多显示器也能正确定位，且绕过「提高指针精确度」的加速度；
> 键盘发**扫描码**而非虚拟键码，尊重**目标机器**的键盘布局。

## 12.5 Phase 0b 实测结论（已在本机跑完）

**测试环境**：Windows 11，20 核，双显示器（主屏 2560×1440 / 副屏 1920×1080）

### 链路各环节耗时

| 环节 | 中位 | 说明 |
|---|---|---|
| 采集（dxcam 有变化帧） | 4.65 ms | 静止帧仅 0.11 ms |
| 分块差分（原生 2560×1408） | 15.4 ms | 已用优化算法，旧算法要 118 ms |
| 分块差分（降到 1280×704） | 4.4 ms | |
| PIL 懒转换 | 6.2 ms | 仅在真有变化时才付 |
| atlas 拼接 + JPEG q60 | 0.4 ms | |

**单帧合计**：原生 29.7 ms（34 fps 上限）／ 降到 1280 是 23.6 ms（42 fps 上限）。
目标 20 fps，**余量充足**。

### 带宽实测（真机采样，真实使用场景）

| 场景 | 更新包中位 | @20fps |
|---|---|---|
| 静止 / 打字（变化块 0.3%） | **3.3 KB** | **0.54 Mbps** ✅ |

| 全屏刷新（滚动长网页） | 整帧 136.7 KB | 10 fps 约 11.2 Mbps |

**结论：办公场景带宽极低（中位 0.5 Mbps），只有全屏刷新才吃带宽。**
这与目标场景（打字、看文档、写代码）高度吻合。

### 对压缩策略的修订

原先按「VPS 带宽 3~5 Mbps」设计的激进压缩方案**已放宽**：

- `target_width` 默认 **0（原生分辨率）** —— 文字最清晰，办公场景带宽完全够
- 保留配置项，带宽吃紧时可设成 Viewer 窗口宽度（如 1280），且**必须走整数倍降采样**
- JPEG 质量区间 40~80，默认 60
- 帧率上限 20 fps
- 自适应降质逻辑保持不变，用于兜底全屏刷新场景

## 13. 风险与预期

| 风险 | 影响 | 应对 |
|---|---|---|
| 公司 EDR / 杀软拦截未签名 exe 🔴 | **项目可能无法落地**（与语言选择无关） | **Phase 0a 先验证**，通过了再投入 |
| 公司 IT 政策 | 在公司设备部署自建远控可能违规 | 建议先自行确认，避免被动发现 |
| 公司防火墙拦非标端口 | 连不上 | 端口回退链 |
| 3~5 Mbps 带宽受限 | 动态画面降质 | 分块差分 + 自适应；定位为办公场景 |
| 境外节点延迟（若为美国） | 操作迟滞 | 建议优先考虑香港节点；Phase 4 可选 P2P 直连 |
| Agent 注入 bug 夺走本机键鼠 | 影响正常工作 | 第 10 节保命措施 + 分阶段实施 |

### 实际体验预期（3~5 Mbps + 境外节点）

| 场景 | 预期 |
|---|---|
| 打字、看文档、写代码、开网页 | ✅ 流畅，接近本地 |
| 拖动窗口、快速滚动长网页 | ⚠️ 有迟滞和降质 |
| 看视频 | ❌ 不现实 |

### 关于 P2P（已评估，暂缓）

若改为 P2P 直连，可绕开 VPS 的 3~5 Mbps 限制与跨境延迟，VPS 只做信令（几十 KB）。但需要在 Phase 1 就实现 UDP 打洞，复杂度明显上升，且公司 NAT 可能打不通（届时仍需回落中继）。

**决策：先中继跑通（保证尽快有可用产品），P2P 留到 Phase 4 可选。**
