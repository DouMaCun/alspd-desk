# Phase 0 手动验证清单

> 目标：在写正式 Agent/Viewer 之前，先确认两件事。
> **这两件事只要有一件过不了，后面的工作都没有意义**，所以必须先做。

| 编号 | 要验证什么 | 为什么关键 | 谁来做 |
|---|---|---|---|
| **0a** | 公司电脑能否连出网络、能连到 VPS 的哪些端口、TLS 是否被中间人、**真实带宽多少** | 决定这条路能不能走通（EDR 拦截 / 防火墙封锁都可能直接否掉方案） | 你在公司电脑 + VPS 上跑 |
| **0b** | 本机采集/差分/编码链路的性能与带宽占用 | 决定压缩参数（分辨率 / 质量 / 帧率） | 已在本机跑完，见下文结论 |

## 一、Phase 0a：侦察（需要你操作）

### 准备：把服务端传到 VPS

在**开发机**（本机）上执行，把服务端脚本传到 VPS：

```powershell
scp tools\probe_server.py root@<你的VPS_IP>:/root/
```

> `probe_server.py` **只用 Python 标准库**，VPS 上不需要装任何依赖。

### 第 1 步：在 VPS 上启动侦察服务端

SSH 登录 VPS，然后：

```bash
# 端口 <1024 需要 root，所以用 sudo
sudo python3 probe_server.py --tls --ports 443,8443,80,8080

# 如果 22 端口也要测，先确认 SSH 不在 22 上；否则会提示端口占用并跳过（不影响其他端口）
```

服务端会打印 **证书 SHA256 指纹**，把它记下来（下一步要用）：

```
[INFO ] 证书 SHA256 指纹：
[INFO ]     ab12cd34...（64 位十六进制）
```

> 如果提示找不到 openssl：`apt install -y openssl`

### 第 2 步：在公司电脑（本机）上运行侦察客户端

**另开一个窗口**（服务端要保持运行），在项目目录下：

```powershell
.\.venv\Scripts\python.exe tools\probe_agent.py `
    --host <你的VPS_IP> `
    --ports 443,8443,80,8080 `
    --expect-fingerprint <上一步记下的指纹>
```

它会依次做 6 件事：

| 步骤 | 测什么 |
|---|---|
| 1/7 | 本机环境（是否域环境、有无管理员权限） |
| 2/7 | 系统代理设置（IE 注册表 + WinHTTP + 环境变量） |
| 3/7 | DNS 解析是否正常 |
| 4/7 | 能否访问知名 HTTPS 站点、**TLS 是否被公司中间人解密** |
| 5/7 | **VPS 的哪些端口能连通**（每个端口同时测明文和 TLS） |
| 6/7 | **代理能否到达 VPS**（HTTP CONNECT / SOCKS5，自动探测系统代理） |
| 7/7 | **真实吞吐量**（上/下行各测 2 次，约消耗 4MB 流量） |

结果会**三处留痕**：控制台打印 + 本地文件 `probe_result_<主机名>.txt` + **回传给 VPS**（这样 VPS 的日志里也有一份完整记录）。

### 第 3 步：把 VPS 上的日志发我

VPS 上会打印出完整报告，格式如下（节选）：

```
[INFO ] [端口连通性]
[INFO ]     18443    {'明文': True, '明文RTTms': 0.7, ...}
[INFO ] [真实吞吐量]
[INFO ]     上行(公司->VPS)   最好 4934.48  最差 4415.06  均值 4674.77  Mbps
[INFO ] 结论速览：
[INFO ]     ✅ 可用端口：18443
[INFO ]     ✅ 上行 4934.48 Mbps —— 压缩策略可据此放宽
```

**把 VPS 上的这段日志发给我**，我据此定压缩参数。

### ⚠️ 几个必须注意的点

1. **吞吐量若显示 > 2000 Mbps，是不合常理的** —— 说明运行端和目标是同一台机器/同一局域网（走了 loopback）。必须对着**真实的 VPS 公网 IP** 测才有意义。
2. **TLS 中间人**：如果第 4 步报告"疑似存在 TLS 中间人解密"，那 `config.toml` 的 `pinned_fingerprint` 必须留空 —— 因为公司代理会替换证书，钉扎会导致连不上。这不影响安全性（我们还有应用层端到端加密，中间人解出来仍是密文）。
3. **本机检测到系统代理**（IE 代理已启用）。我们的工具**默认先直连**，直连不通时才自动走代理 —— 所以如果公司要求必须经代理出网，第 6 步会告诉你哪个代理可用，把结果填进 `config.toml` 的 `proxy` 即可。
4. **流量消耗**：吞吐量测试默认每方向 2 次 × 2MB ≈ 8MB。如果 VPS 是按流量计费的，可以用 `--no-throughput` 跳过，或 `--bytes 524288 --iters 1` 减小。

### 如果第 5 步全部不通、但第 6 步有代理可用

**方案仍然可行**，不要下"这条路走不通"的结论。在**两端**（Agent 与 Viewer）的 `config.toml` 里加上：

```toml
[common]
proxy = "socks5://127.0.0.1:10808"   # 换成你实测可用的那个
```

（默认的 `"auto"` 理论上会自动兜住，但显式指定更稳妥。）

## 二、Phase 0b：性能实测（已在本机跑完）

### 结论摘要

**本机配置**：Windows 11，20 核，双显示器（主屏 **2560×1440**，副屏 1920×1080）

| 采集后端 | 有新帧时 | 画面静止时 |
|---|---|---|
| **dxcam (DXGI)** ✅ 选它 | **4.65 ms** | **0.11 ms** |
| mss (GDI) | 33 ms | 33 ms（**无论是否变化都要付**） |

**dxcam 比 mss 快 7 倍，静止时便宜 300 倍。** 已确定用 dxcam，mss 作为回落。

### 关键的三档分辨率对比

| 目标分辨率 | 预处理 | 差分 | 单帧合计 | 上限 | 整帧 q60 | 办公场景 P90 更新包 |
|---|---|---|---|---|---|---|
| **2560×1408 原生** | 0.01ms | 18.0ms | **29.7ms** | 34fps | **136.7 KB** | 31.9 KB |
| 1920×1056 | **34.7ms** ⚠️ | 9.6ms | 50.3ms | 20fps | 82.4 KB | 2.4 KB |
| **1280×704** | 13.3ms | 4.4ms | **23.6ms** | 42fps | **34.1 KB** | 1.0 KB |

### 🔴 一个反直觉的陷阱

**1920 是最差的选择，比原生还慢。**

原因：2560→1920 不是整数倍，只能走通用的 `resize BOX`（**34.7ms**）；
而 2560→1280 正好是 2 倍，走 `reduce(2)` 盒式滤波（13.3ms）。

> **结论：降采样必须走整数倍。** 非整数倍的 resize 代价高到会吃掉全部收益。

### 其他实测结论

- **atlas 编码比逐块编码省 44% 体积**，且只需一次编码调用 → 确定采用 atlas 方案
- **WebP 编码 179ms、PNG 535KB** → 直接淘汰
- **JPEG q60 是甜点**：q45 体积只小一点但画质明显下降，q75/q80 体积涨得快
- **差分算法优化**：把颜色通道并入 tile 归约，原生分辨率下 **118ms → 15.4ms（7.7 倍）**，检出结果完全一致（都是 209 块）。这是 numpy 对小尾轴归约开销极高的经典陷阱。
- **Desktop Duplication 每个显示器只允许一个复制器** → 被 OBS/录屏占用会失败，RDP 会话不支持，所以**必须保留 mss 回落路径**

### 办公场景带宽（关键好消息）

真机采样（画面大部分静止）：

| 场景 | 更新包中位 | @20fps 带宽 |
|---|---|---|
| 静止 / 打字（变化块 0.3%） | **3.3 KB** | **0.54 Mbps** ✅ |
| 全屏刷新（滚动长网页） | — | 整帧 136.7KB → 10fps 约 11.2 Mbps |

**办公场景带宽极低（P50 仅 0.5 Mbps），只有全屏刷新才吃带宽。**
这正好和你的使用场景吻合 —— 打字、看文档、写代码都几乎不耗带宽。
